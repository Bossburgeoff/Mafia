## 2. Теоретические сведения

**Система контроля версий (СКВ)** — инструмент, хранящий историю изменений файлов и позволяющий нескольким людям работать над одним проектом.

**Виды СКВ:**

| Вид | Принцип | Особенность |
|---|---|---|
| Централизованные | один общий репозиторий | работа невозможна без связи с сервером |
| Распределённые | у каждого полная копия репозитория | можно работать автономно, слияние гибче |

**Основные понятия:**

| Понятие | Определение |
|---|---|
| Репозиторий | хранилище файлов и истории изменений |
| Фиксация (коммит) | сохранение набора изменений с описанием |
| Ветка | независимая линия разработки |
| Слияние | объединение изменений из одной ветки в другую |
| Конфликт | ситуация, когда одни и те же строки изменены по-разному |
| Запрос на слияние | предложение внести изменения из ветки в основную, с проверкой |
| Код-ревью | проверка изменений другим участником |

**Модель ветвления в проекте:**

| Ветка | Назначение |
|---|---|
| `main` | рабочая версия, прямые коммиты запрещены |
| `develop` | интеграционная ветка |
| `feature/<модуль>-<номер задачи>` | новая функциональность |
| `fix/<номер задачи>` | исправление дефекта |
| `docs/<тема>` | документация |

**Требования к фиксации:** сообщение формата `<тип>(<область>): <что сделано> #<номер задачи>`. Типы: `feat`, `fix`, `docs`, `test`, `refactor`.

**Управление конфигурацией** как процесс описано в ГОСТ Р ИСО/МЭК 12207-2010: определение конфигурации, идентификация элементов, контроль изменений, учёт состояния, аудит.

## 4. Порядок выполнения

### Шаг 1. Проверить доступ и настройки

- Убедиться, что есть доступ к репозиторию.
- Указать в настройках имя и адрес — они попадают в историю коммитов.
- **Результат:** первый коммит под своим именем.

### Шаг 2. Отработать ветвление

- Создать ветку `feature/<модуль>-<номер задачи>`.
- Внести изменение, сделать фиксацию с сообщением по формату.
- **Результат:** ветка с осмысленной историей.

### Шаг 3. Подготовить запрос на слияние

- Отправить ветку на сервер.
- Создать запрос на слияние в `develop` с описанием: что сделано, как проверить.
- **Результат:** открытый запрос на слияние.

### Шаг 4. Провести код-ревью

- Взять запрос на слияние другого участника.
- Оставить не менее двух замечаний или подтверждений по существу.
- Внести правки по замечаниям к своему запросу.
- **Результат:** ревью проведено, правки внесены.

### Шаг 5. Разрешить конфликт слияния

- Смоделировать конфликт: двум участникам изменить одну строку в разных ветках.
- Разрешить конфликт вручную, объяснив выбор итогового варианта.
- **Результат:** конфликт разрешён, слияние выполнено.

### Шаг 6. Слить изменения

- Выполнить слияние после одобрения ревьюера.
- Убедиться, что история сохранилась и вклад каждого виден.
- **Результат:** изменения в `develop`.

### Шаг 7. Оформить отчёт

- Описать выполненные операции, привести граф истории, объяснить решения при конфликте.
- **Результат:** отчёт приложен.

## 5. Требования к отчёту

Отчёт содержит:

1. Титульный лист (дисциплина, работа, группа, ФИО, дата).
2. Цель работы.
3. Ссылку на репозиторий.
4. Список своих коммитов с сообщениями.
5. Ссылки на созданный и проверенный запросы на слияние.
6. Описание конфликта слияния: в чём состоял, как разрешён, почему выбран такой вариант.
7. Изображение графа истории репозитория.
8. Перечень нарушений регламента, если были, и их причины.
9. Заполненный чек-лист приёмки.
10. Вывод.
